# AI Tutor Design

## Product

AI Tutor is a command-line agent that answers questions about artificial intelligence and machine learning. It is intended for developers and technical learners who want a clear explanation backed by current, inspectable sources.

The product promise is narrow: **ask one AI question and receive one concise, evidence-backed lesson**.

## User experience

```bash
uv run ai_tutor.py "Why does retrieval-augmented generation reduce hallucinations?"
```

The answer contains:

- a direct answer;
- a concise explanation with inline citations such as `[S1]`;
- an example when useful;
- a “What to remember” takeaway;
- uncertainty when the evidence is incomplete or disputed;
- an optional check-your-understanding question;
- a Sources section rendered from the retrieved evidence.

The tutor covers AI/ML concepts, LLM applications, agents, evaluation, infrastructure, research, safety, and related engineering practices. Inputs are expected to be AI-related; general-purpose assistance is outside this take-home's scope.

## System boundary

The implementation keeps the starter's core architecture:

1. Typer accepts one question and an optional model name.
2. LangChain `create_agent` runs the verified Nebius-hosted Qwen 30B Instruct model.
3. One wrapped Tavily search tool retrieves current evidence.
4. A per-run source registry assigns IDs such as `S1` and `S2`.
5. Deterministic code validates the model's cited IDs.
6. The CLI appends source titles and URLs from the registry and prints the answer.
7. LangSmith records the LangChain run when tracing is configured.

No other service or persistence layer is required.

## Grounding contract

For every substantive answer:

- Tavily must return at least one usable result.
- The model receives only normalized source records: ID, title, URL, and a bounded snippet.
- Factual teaching points cite one or more source IDs inline.
- Every cited ID must exist in the current run's source registry.
- The final URLs are rendered by code, not generated by the model.
- If retrieval fails, returns no sources, or the answer contains missing or invalid citations, the run ends with an explicit error instead of presenting an ungrounded lesson.

This contract proves that citations originate from retrieved results. It does not claim that string validation proves semantic entailment. The sample answers will therefore also receive documented human review against their cited snippets.

## Retrieval policy

- Prefer official documentation, standards, and original research.
- Permit exactly one basic-depth search per tutor run.
- Detect explicit current-time wording such as “recent” or “latest” and apply a
  compact primary-domain filter.
- Discard returned URLs that do not match an active domain filter.
- Return at most five results from the search.
- Keep raw page content disabled to control latency and context size.
- Include Tavily usage and request metadata for debugging.
- Preserve Tavily provider errors instead of relabeling them as empty retrieval.
- Inject the current date into the tutor prompt so time-relative questions are interpreted correctly.

## Tutoring behavior

LangChain sends the tutor instructions as a system-role message and the question as a user-role message. The system-message content has three flat XML sections—`instructions`, `evidence_rules`, and `response_format`—with no literal `<system>` wrapper. The tutor should lead with the answer, define necessary jargon, use a concrete example where it helps, and distinguish established facts from judgment or active debate. It should match the question's apparent technical depth without adding a learner-profile system or conversation memory.

The default model is `Qwen/Qwen3-30B-A3B-Instruct-2507`, which Nebius identifies as tool-capable without a reasoning mode. Four consecutive full-agent fixture runs produced visible, structurally valid answers before it replaced Kimi K2.6. The application does not add a retry or fallback generation path.

The response headings are:

1. `Answer`
2. `Explanation`
3. `Example` or `Uncertainty` when useful
4. `What to remember`
5. `Check yourself` when useful
6. `Sources`, rendered deterministically

## Observability contract

LangSmith uses its standard environment configuration:

- `LANGSMITH_TRACING`
- `LANGSMITH_API_KEY`
- `LANGSMITH_PROJECT`
- `LANGSMITH_WORKSPACE_ID` only when one key can access multiple workspaces
- `LANGSMITH_ENDPOINT` only when the account's region requires it

Each tutor invocation has:

- one generated UUIDv7 used as run ID, trace ID, and one-turn thread ID;
- run name `ai-tutor-answer`;
- tags `ai-tutor` and `cli`;
- metadata containing the selected model, the UUID as `cli_run_id`, and the
  UUID as the LangSmith `thread_id` on root and child runs;
- the UUID passed as the root LangChain `run_id`, which makes it the LangSmith
  `trace_id`;
- visible CLI output stating whether tracing is enabled and showing the shared
  `Run ID / LangSmith Trace ID / Thread ID`.

The application remains single-turn and does not persist chat history. Each
invocation is therefore one LangSmith thread containing one trace. The thread
metadata exists for documented LangSmith grouping, filtering, token, and cost
behavior—not as a claim of application memory.

Tracing is optional for ordinary local use but mandatory for the submission's recorded live demonstration. Explicitly enabling tracing without the required configuration is a startup error.

## Failure behavior

- Missing Tavily or Nebius credentials: explain the missing variable and exit nonzero.
- Invalid LangSmith configuration when tracing is enabled: explain the missing variable and exit nonzero.
- Tavily or model failure: show a concise error and the run ID; do not produce a fallback lesson.
- No usable Tavily results: report insufficient evidence; do not let the model answer from memory.
- Missing or invented citation IDs: reject the answer and show the invalid IDs.
- Keyboard interruption: exit cleanly with status 130.

## Verification

Automated tests cover:

- source normalization and stable IDs;
- deduplication of repeated URLs;
- valid citations;
- missing, malformed, and unknown citations;
- empty retrieval;
- environment validation;
- deterministic source rendering;
- provider-error propagation;
- filtered-domain enforcement and current-question detection;
- the one-search and structured-output prompt contracts.

Live verification uses three fixed questions:

1. A foundational AI concept.
2. A current AI engineering question that requires fresh retrieval.
3. A nuanced misconception where the tutor should state limits or uncertainty.

Each live result is manually checked against its cited snippets, correlated with its LangSmith run, and recorded in `build_log/06-final-acceptance-and-release-audit.md`.

## Non-goals

- Chat history or persistent learner profiles
- Web or desktop UI
- Multiple agents or subagents
- Deep Agents, skills, memory, or filesystem tools
- Database, vector store, caching, or background jobs
- Additional search or inference providers
- Autonomous curriculum planning
- LLM-as-judge evaluation
- Deployment
